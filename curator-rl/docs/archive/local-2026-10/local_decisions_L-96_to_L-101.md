# Local decisions L-96 … L-101 (archived, see README.md)

## L-96 (written as D-96) — Phase F: the scheduler around a real GRPO trainer; design, protocol for the GPU gates (written before any GPU run)

- Date: 2026-10-10. Built and verified on CPU only; no GPU evidence yet. Code: `cost/{ledger,meter}.py`, `trainer/{prompt_stream,reward_wrapper,round_controller,checkpoint,report_eval,trl_adapter}.py`, `scripts/{run_training,phase_f_matrix,smoke_local}.py`, `experiments/analysis/phase_f_gates.py`, `notebooks/kaggle_phase_f.ipynb`; tests `test_trainer_core.py`, `test_scheduler_checkpoint.py`, `test_phase_f_gates.py` (381 pass).
- **Design decisions.** (1) *Exact mixture, lag 0.* TRL 1.15.0 (source read, `docs/TRL_SPIKE.md`) calls `_generate_and_score_completions` once per optimiser step when steps_per_generation == gradient accumulation and num_iterations == 1; the adapter overrides it and supplies the step's prompts from the round controller (each prompt repeated G times, contiguous), so the scheduler's weights for round t are decided after round t-1 is complete and no dataloader prefetch can draw a prompt early. The dataloader is only a clock; its rows are ignored. The constructor refuses any other generation geometry. (2) *Realised shares.* `PromptStream` converts weights to exact integer quotas (largest remainder, same rule as the simulator); the scheduler is told the REALISED share. (3) *Cost.* Step wall time is measured with a device synchronise (`on_step_begin` to `on_step_end`); the verifier-pool wall time is attributed by per-item verifier seconds, the rest by a token-share model (completion tokens + 0.1 x prompt tokens), rescaled to the measured total (COST_MODEL section 3); scheduler time inside a step is charged as overhead and subtracted from the step so it is not charged twice; generation and update cannot be separated inside a TRL step and are charged together as `train_gen`; time between steps is recorded as unattributed and not charged. The budget stops training at the first optimiser step whose charge reaches B (SPEC section 4). (4) *Verification* runs in a 4-thread pool (D-87c); verifier crashes count as wrong answers and are logged. (5) *Checkpoints* at round boundaries: LoRA weights, optimiser state and one atomic JSON with the scheduler, prompt stream, ledger and meter. Model-side randomness (torch/CUDA/vLLM) is not restored, so a resumed run is statistically, not bit-for-bit, equivalent; everything else is exact (tested). (6) *Calibration is OFF for every Phase F run* (`calib.enabled` forced false): the controller raises if a calibrating scheduler has no runner. (7) Constant learning rate, no warm-up, DAPO loss, beta 0, group-scaled advantages, top_k 0, temperature 1.0, fp16, LoRA r16/alpha32 on all linear layers; R = 2 steps per round, P = 16, G = 8, 512 completion tokens (verification caps per environment as in the pilot).
- **Bug found by this phase.** `DiscountedUCB.get_state` did not include the latest signal vectors, so a restored scheduler skipped its status constraints for one round (first weights after a restart were unconstrained). Fixed; `test_scheduler_checkpoint.py` now replays recorded observations through every scheduler (uniform, static, LP, UCB, SEC, DUMP, Curator), snapshots through JSON, and requires identical mixtures after resume.
- **CPU verification done.** Real TRL 1.15.0 with a tiny model (SmolLM2-135M) end to end: generation, parallel verification, step timing, round observations, budget stop (overshoot 0.0032 GPU-h = one step), unattributed time 0.01%, kill-and-resume from a round boundary (model state restored, rounds 3-6 continue the log), the plain-TRL reference, and the uncharged report evaluation. TRL's fused log-prob kernel needs Triton (Linux only), so locally it is replaced by a plain-PyTorch stand-in (`scripts/smoke_local.py`); Kaggle uses the real kernel.
- **GPU protocol (pre-registered now).** Learning rate: pilot on tuning seed 99, uniform, B = 0.25 GPU-h, rates 1e-5, 3e-5, 1e-4; the highest dev-macro gain (end minus start) wins, ties to the lower rate; seeds 0-2 are never used for tuning. Main runs: B = 1.0 GPU-h (adjustable before the first main run, not after), seeds 0, 1, 2, Qwen2.5-0.5B-Instruct, vLLM colocate. Evaluation: uncharged greedy pass rate on the dev split, 96 fixed prompts per environment (60 for MBPP), at start and end; primary metric = equal-weight macro over gsm8k, math35, mbpp, countdown.
  - Gate 3 (per uniform seed): dev macro gain >= 2 SE (binomial SEs of start and end, combined) AND GSM8K training pass rate (last 10 rounds minus first 10 rounds) >= +5 points; the kill-and-resume run continues the same log to the budget; peak memory recorded.
  - Gate 4 (3 paired seeds, uniform through the controller vs plain TRL on the same prompts for the same number of steps): macro score difference and mean per-step reward difference, each with a 95% t interval over the 3 paired differences; PASS only if the whole interval lies inside the margin (delta_S 0.01, delta_R 0.01), FAIL if the mean is outside it, otherwise INCONCLUSIVE; plus realised vs requested share <= 2 points averaged over the run, curator overhead < 2% of charged cost, update lag 0 by construction.
  - Gate 5: (a) per-environment attributed seconds per prompt in the mixed runs within 10% of solo-environment runs (10 steps each); (b) ledger charge within 2% of measured loop time; (c) unattributed < 3%; (d) unit-cost CV across rounds < 10%; (e) MATH35 costlier than GSM8K.
- **Stated in advance so a failure is not re-interpreted afterwards.** (i) The score margin 0.01 is smaller than the standard error of a macro score on 96 prompts per domain (about 0.02), so the Gate 4 score test is expected to be INCONCLUSIVE with 3 seeds. That outcome is reported as such; the fixes are more seeds or a larger evaluation, never a wider margin. (ii) Gate 5(a) compares per-prompt cost in a mixed batch (fixed update cost shared) with a solo run (fixed cost borne alone); it may fail for that reason. If it does, it is reported as failed, and a regression of step time on composition across rounds is run as a labelled diagnostic, not as a replacement. (iii) The unit-cost CV across rounds mixes prompt content with measurement noise (D-86c) and may fail for that reason; it is judged as written.
- **Open issue for Phase G (calibration on GPU), not addressed here.** The noisy arm trains on GSM8K prompts, so it has no calibration slice of its own: a slice is shared by the `gsm8k` and `noisy` arms. The simulator results of D-95 gave the noisy arm its own slice, which the real system cannot. Own-slice credit (C2) attributes a slice's gain by compute share per window, so shared-slice gains would be credited to the noisy arm too; the regression must be extended to several arms per slice (the C2d form) and re-validated on a simulator where the noisy arm shares the GSM8K slice, with a new pre-registration, before any Phase G run.

## L-97 (written as D-97) — Shared calibration slice: spurious-arm detection does not survive it; joint credit helps only a little (diagnosis, nothing adopted)

- Date: 2026-10-11. Tuning seeds 0-49 only; refit scenarios; the adopted Curator (claim_stale targeting, 2 slices). Evidence: `reports/analysis/shared_slice_diagnosis.{json,md}`.
- Why: on real hardware the noisy arm trains on GSM8K prompts, so it can only be checked on the GSM8K calibration slice (D-96 open issue). Every simulator result on detection so far (D-74, D-95) gave it a private slice.
- Built: `calib.shared_slices` (arm -> slice it shares; default empty) and `calib.credit` ("own" = the existing per-arm regression, D-73; "joint" = all arms of a slice fitted together, `JointSliceCredit`); targeting now returns slice names, counting a shared slice once. With no shared slice the code is behaviour-neutral: the D-93 tuning report reproduces bit for bit, and `JointSliceCredit` equals `OwnSliceCredit` exactly on private slices (tests in `test_joint_credit.py`). Defaults keep the adopted configuration unchanged.
- Result (mean over the three scenarios):

| setting | noisy detected | GSM8K flagged | false-flag rate | calibration cost | score |
|---|---|---|---|---|---|
| private slice, own credit (the D-95 idealisation) | 0.78 | 0.00 | 0.017 | 3.4% | 0.326 |
| shared slice, own credit (the real system today) | **0.07** | **0.11** | **0.112** | 3.2% | 0.318 |
| shared slice, joint credit | 0.15 | 0.04 | 0.035 | 3.2% | 0.319 |

- Reading: (1) The D-95 detection result does not transfer to the real portfolio as it stands: with a shared slice the own-slice rule credits the noisy arm with GSM8K's genuine gains, the robust proxy-to-gain scale rises, and the arm that really learns (GSM8K) is flagged instead in 11% of runs. (2) Joint credit removes most of that harm (GSM8K flagged 4%) but recovers little detection. Hypothesis, not yet tested: Curator's allocation keeps the two arms' shares nearly proportional, and about 4 calibration windows per run cannot separate two coefficients. (3) Hypothesis H4 (spurious-reward detection) is therefore NOT supported for an arm that shares its inputs with a real arm. D-95's claim stands only for spurious arms with a private slice.
- Consequences: no configuration change. `shared_slices` must be set to {noisy: gsm8k} for any GPU run with calibration, and with the current mechanisms calibration should not be expected to catch the noisy arm there. Candidate directions, each needing its own pre-registration on fresh seeds (>= 700) and none acted on: (a) a reward-validity audit: run each arm's reward function on the calibration completions of its slice and test agreement with the slice's verifier (a spurious reward agrees at chance level; needs no share variation and no extra generation); (b) deliberate share perturbation between the arms of a shared slice so the joint regression becomes identifiable (costs budget); (c) accept the narrower claim and report the shared-slice failure as a limitation.

## L-98 (written as D-98) — Reward-validity audit: design and pre-registration (FROZEN 2026-10-11)

- Date: 2026-10-11. Full text: `docs/prereg/D98_reward_validity_audit.md`. Option (a) of D-97, chosen by the owner.
- Summary: an opt-in audit (`calib.audit.enabled: false` by default) that runs each arm's own reward function on answers the calibration evaluation already generated for its slice and correlates it with the slice's gold verifier (phi over unique (item, answer) pairs; invalid iff the one-sided 95% upper bound < 0.3 with >= 100 pairs). It is reward-validity evidence, kept separate from benchmark-gain evidence. Threshold fixed from the rule's operating characteristics alone (no experiment data). Candidate selection on tuning seeds 0-49; confirmation once on fresh seeds 700-799 with criteria C1-C5.
- **Frozen 2026-10-11** on the owner's instruction to choose the best approach and proceed. Pre-freeze review (statistics of the rule only, no data) added: (1) operating characteristics under repeated looks (6 looks): a reward with <= 30% label flips is ever flagged in 0.6% of runs, a random reward in 99.6% (91% at the first look), so phi0 = 0.3, z = 1.645, n_min = 100 are unchanged; (2) an explicit intersection-union statement (all criteria in all scenarios, no further correction); (3) a real-data check on the base model's calibration answers before any GPU use. From here on sections 3-6 of the document do not change. Also: `calib.shared_slices` and `calib.credit` (D-97) and the audit settings are declared explicitly in `configs/base.yaml` (SPEC rule: no Python defaults for hyperparameters); the declared values reproduce current behaviour.

## L-99 (written as D-99) — D-98 outcome: no eligible candidate at Stage T; Stage E not run; D-97's narrower claim stands

- Date: 2026-10-11. Run as frozen in D-98. Evidence: `reports/analysis/audit_tune.{json,md}` (Stage T, tuning seeds 0-49), `reports/analysis/audit_diagnosis.{json,md}` (reason attribution, same seeds, exploratory).
- Implementation (behind `calib.audit.enabled: false`): `calibration/audit.py` (pooled unique-pair phi rule), audit verdicts reported in `CalibrationReport.reward_audit`, separate S5 reason "S5 reward invalid (audit)" in the status machine (gain path unchanged), simulator audit pairs from the existing paired evaluation (no extra random draws), charged ledger category `calib_audit`, real-environment helper `trainer/audit_pairs.py`. With the audit off, the D-93 and D-97 reports reproduce bit for bit; 14 new tests; 401 pass.
- Stage T (shared slice, audit on): cand_own detects 0.987, GSM8K flagged 0.167, false-flag rate 0.133; cand_joint detects 0.980, GSM8K flagged 0.100, false-flag rate 0.055; both cost 3.2%. Neither meets GSM8K <= 0.05 and false flags <= 0.05, so by the frozen rule **no candidate is chosen and Stage E is not run**. Seeds 700-799 stay unused.
- Diagnosis (tuning seeds, explains the outcome, changes nothing): every GSM8K false flag came from the gain-mismatch test, none from the audit; adding the audit raised GSM8K gain flags from 0.04 to 0.10 (the noisy arm is demoted, GSM8K's share rises, and the unidentifiable shared-slice gain test misfires more). An exploratory audit-only arm (gain flags off) detected 0.973 with no false flags, which is not a result.
- Consequence: D-97's narrower claim stands (spurious-reward detection holds only for an arm with a private slice). The audit code stays, disabled by default. A follow-up hypothesis, using gain evidence only where it is identifiable (private slices) and the audit for arms on shared slices, is proposed as D-100 (`docs/prereg/D100_shared_slice_evidence_rule.md`), not frozen, on seeds 800-899, with D-98's criteria unchanged.

## L-101 (written as D-101) — Phase F on Kaggle: smoke test and learning-rate pilot outcome; staged launch of the main matrix

- Date: 2026-10-12. Evidence pasted from the Kaggle notebook (`notebooks/kaggle_phase_f.ipynb`); not yet stored as report files.
- Smoke test (curator, B = 0.05 GPU-h, vLLM, Tesla T4): 4 steps, 2 rounds, stopped with overshoot 0.0048 GPU-h (17 s, less than one step), unattributed time 0.1%, peak memory 6.3 GB, step time 41-52 s (49.5 s mean on the full portfolio; the 42.2 s of D-83 was GSM8K only). So B = 1.0 GPU-h buys about 73 steps = 36 rounds at R = 2. Greedy dev evaluation works (macro 0.234 at 16 prompts per environment; countdown 1 of 16, consistent with the 0/1,024 sampled answers of D-87).
- Learning-rate pilot as pre-registered in D-96 (uniform, tuning seed 99, B = 0.25 GPU-h = 18 steps, dev macro gain): 1e-05 +0.0076, 3e-05 +0.0076 (exact tie), 1e-04 +0.0003. Rule: highest gain, ties to the lower rate -> **learning rate 1e-5**. The first attempt at 1e-05 died within seconds when two vLLM engines started on the two GPUs at once; it was re-run alone and completed (exit 0); the queue launches are now staggered by 90 s. Applied exactly as written.
- Interpretation, stated now: the pilot cannot discriminate between rates. 18 steps is too little training and the dev score has a standard error of about 0.02, so the three gains are indistinguishable; the tie-break decided. It follows that Gate 3 at 1e-5 and B = 1.0 is a real test that may fail (a macro gain of >= 2 SE is about +0.04; 73 steps at 1e-5 may not deliver it). A failure will be reported as a failure.
- Launch plan (no change to the protocol; it only orders the runs): run uniform_s0 and uniform_s1 in parallel first, evaluate Gate 3 on those seeds with `phase_f_gates.py`, then continue with the rest of the matrix in the same notebook. All three seeds are run whatever the first two show; stopping early to revise LR or B is a documented protocol revision, with Gate 3 recorded as not met for the original setting.
